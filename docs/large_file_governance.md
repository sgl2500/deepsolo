# 大文件治理规范

本文定义 DeepSolo 大文件的判定标准、拆分原则和执行路线。当前重点对象是 `packages/visual/src/systems/BattleSystem.ts` 与 `packages/visual/src/systems/MapRenderer.ts`。

## 判定标准

| 级别 | 行数 | 处理要求 |
| --- | ---: | --- |
| 正常 | `< 800` | 无特殊要求 |
| 关注 | `800 - 1500` | 新增功能前优先评估是否拆模块 |
| 技术债 | `1500 - 2200` | 必须登记到技术债清单，并准备拆分计划 |
| 高风险 | `> 2200` | 不建议继续直接堆功能；新增功能应优先落到拆分后的模块 |

## 拆分原则

1. **先文档后拆分**：先写清楚职责边界、公共 API、迁移顺序，再动代码。
2. **保持行为不变**：第一阶段只搬代码，不改玩法、不改 UI、不改数据格式。
3. **按调用方向拆**：主系统保留状态机和协调职责，渲染、输入、计算、配置迁移到子模块。
4. **每拆一块就验证**：拆分后必须执行 `npm run check`，必要时手动验证对应场景。
5. **避免大爆炸 PR**：单轮拆分最好只处理一个职责块，例如“战斗 HUD”或“家具编辑器存储”。

## 允许的大文件例外

在以下情况下，可以临时保留大文件：

- 当前仍处于玩法原型快速迭代期。
- 文件已有明确拆分计划，并记录在技术债清单。
- 本轮需求只修 bug，拆分会显著增加回归风险。

但例外不代表继续堆功能。超过 2200 行的文件，每次新增功能前都要优先考虑拆分落点。

## 标准拆分流程

1. **做函数盘点**：列出函数职责、输入输出、依赖状态。
2. **划分模块边界**：区分状态、渲染、输入、计算、持久化。
3. **先抽纯函数**：碰撞、范围、伤害、坐标换算等优先迁移。
4. **再抽渲染器**：HUD、菜单、overlay、特效等迁移到 renderer/helper。
5. **最后缩主类**：主类只保留生命周期、状态机和子模块调度。
6. **更新文档**：每完成一块，更新对应 refactor plan 和 `codex.md`。

## 交付要求

当某个大文件拆分完成后，需要满足：

- 主文件低于 1200 行，或有明确剩余原因。
- `npm run check` 通过。
- 对应文档中的迁移阶段标记完成。
- 正常模式和编辑模式手动回归通过。
